01概述与设计原则

ComfyUI Agent Workbench 让用户用自然语言构建、修改、运行节点式生成工作流。职责切分为两层：Agent（Codex CLI / Claude Code）只做一件事——生成与修改节点图，它产出图变更提议（Proposal），在画布上以高亮 diff 预览，用户一键应用或忽略，每次应用形成不可变的版本快照；节点的实际执行与 Agent 无关，由后端 DAG 执行器经 Model Gateway 调用真实模型 API（如 Seedance 2）完成。运行消耗 API 配额（真金白银），凡由 Agent 发起的运行必须经过确认弹窗。

四条设计原则（全系统遵守）

  1. 先审后行（Propose-then-Apply） — Agent 对图的任何写操作都以 Proposal 形式呈现，画布预览 + 变更清单 + 可展开 diff，绝不静默落盘。
  2. 最小变更（Minimal Diff） — 修改与修复只触碰必要的节点/边/参数。如原型中的修复案例：仅替换 Load ControlNet 的一个 model 参数。
  3. 成本守门（Cost Gate） — 节点执行是计费的 API 调用。Agent 发起的运行需用户确认（版本、次数、预计 API 调用与成本、可中断性）；用户手动点「运行 Queue」不需要。
  4. 全程可追溯（Traceable） — 版本栈记录每次变更的来源（agent / 手动 / 修复 / 恢复），运行记录关联版本，随时回滚。

关键前端决策

  • 后端是唯一事实源。前端不本地计算版本/diff；所有状态变更由 WS 事件驱动，REST 仅用于初始加载与显式动作。断线重连后以 GET /api/workspaces/{id}/state 全量对账。
  • 画布渲染自研（不用 LiteGraph）。v1 画布只读，仅需渲染 + 叠加态，自研 SVG/DOM 方案（原型已验证）远轻于引入 LiteGraph；布局坐标由后端 Graph Service 自动排版给出。
  • 提议预览是叠加层。pending Proposal 渲染为当前图之上的虚影/高亮层，不修改 store 中的图数据——「忽略」即移除叠加层，零回滚成本。
  • 乐观 UI 仅限纯本地交互（输出选中、面板开合）；一切涉及图与运行的动作等待后端事件确认。

04后端架构

Rust 单二进制异步服务，绑定 127.0.0.1:8787（不监听外网）。选型：axum + tokio（HTTP/WS）、sqlx + SQLite（WAL）、reqwest 对接各模型 API、serde + jsonschema 校验 Agent 输出。五个核心服务 + 存储层（各为独立 crate）：

服务职责
AgentOrchestrator每工作区一个 Agent 会话；经 Runtime 层管理 CLI 进程生命周期（懒启动、空闲回收、崩溃重启）；每轮组装会话上下文、解析 CLI 事件流、接收并校验产出；执行守门策略（§09）；把 CLI 过程状态转为 agent.status 事件。
GraphService图的规范模型（§06）；diff 校验与应用（原子）；版本栈（提交/撤销/恢复）；图→可执行计划编译（拓扑序 + 每节点的 provider 调用描述）；自动布局（分层 DAG 排布，给前端坐标）。
RunServiceDAG 执行器：按拓扑序执行节点，每个节点经 Model Gateway 调用对应模型 API，中间产物（图/视频/文本）在节点间传递；单次 Queue 与 Sweep 序列；进度聚合为 run.* / node.* 事件；中断（取消进行中调用 + 后续节点）；失败时捕获错误上下文交给 Orchestrator 触发诊断。
ModelGateway统一 provider trait：invoke(node_type, inputs, params) → outputs。providers/：seedance2（视频）、图像、LLM 等；密钥持有、重试/限流/超时、异步任务轮询（视频生成分钟级）、成本计量；维护能力目录（catalog）：各 provider 可用模型/版本/参数域。
NodeRegistry节点库：每个节点类型 = 一个模型 API 能力的封装（schema：输入/输出端口、参数域、provider 绑定）。TopBar 的节点数来源于此；也是 Proposal 校验与 ctx/node_defs/ 的真理源。节点声明能力、绑定可换——新模型上线 = 新增 provider + 登记节点，不动核心。
StorageSQLite（WAL）存元数据；图快照与 proposal 以 JSON 文件存于工作区目录；输出由 Gateway 下载落盘到工作区 outputs/，表中存引用路径。

05Agent 编排与 Runtime 协议

不引入 MCP。后端内置 Runtime 层（统一 trait：start(session) / send(turn) / events() / cancel()），以各 CLI 的原生 headless 协议直连：CodexRuntime 拉起 codex exec --json、ClaudeCodeRuntime 拉起 claude -p --output-format stream-json，解析 stdout JSON 事件流（思考/工具步骤摘要 → agent.status，原型中「正在规划图变更…」即来源于此）。CLI 与后端的数据交换靠会话工作目录的文件契约：后端每轮把上下文物化进 ctx/，CLI 用自带文件工具阅读检索，并把结构化产出写进 out/。职责边界：CLI 只规划与推理——它的全部产出就是节点的生成与修改（ops）与运行请求，真实的图、数据库与模型 API 它碰不到，会话目录是其唯一可写区域。

Skill 机制（prompt + skill 驱动，参考 Claude 设计环境的做法）

CLI 不靠硬编码工具获得能力，而靠注入的指令文档（skill）：每个 skill 是一份自包含的 Markdown（流程指引 + 产出 schema + 少量正反例）。Orchestrator 按用户意图路由，每轮只注入命中的 1–2 个 skill，保持上下文精简；skill 随仓库版本化，迭代提示词不动代码。

Skill职责与产出
skills/create_workflow.md从需求生成完整节点图：选节点、连线、填参（含 prompt）。产出 out/proposal.json（kind=create）。
skills/modify_workflow.md增量修改：最小 diff 原则、保留现有节点、插入分支的连线规范。产出 kind=modify。
skills/fix_error.md读 ctx/run_error.json + ctx/catalog.json 定位根因，产出最小修复（kind=fix，尽量单 op）。
skills/sweep.md参数试验计划（seed / 参数网格）与结果选优。产出 out/run_plan.json 与选优结论。
skills/node_library.md节点库总览与选型指引（何时用 Seedance 2 而非图像模型、常见链路模式）；始终注入。

会话文件契约（每轮由后端组装）

路径方向内容
ctx/graph.json注入当前版本图（节点、参数、边）+ 版本标签。
ctx/node_defs/注入节点库定义（NodeRegistry 导出）：常用节点速查表 + 按类别分文件的全量索引，CLI 按需检索——不全量进上下文。
ctx/catalog.json注入Gateway 能力目录：各 provider 可用模型/版本/参数域（如 seedance-2.0-pro）。修复流程的关键依据。
ctx/skills/注入本轮命中的 skill 文档（见上），随任务类型路由。
ctx/run_error.json注入失败运行的上下文：节点、参数、原始 traceback、各节点耗时。
ctx/instructions.md注入系统约定：产出格式 schema、最小变更原则、禁止事项。
out/proposal.json产出*图变更提议（格式见下）。后端解析校验后入库并推给前端，不直接改图。
out/run_plan.json产出*运行请求（次数、seed 列表等参数覆盖）。触发前端确认弹窗，用户确认前不执行。

* 产出均为间接生效：落到用户审核流，后端是唯一真实写方。校验失败时后端把错误写回会话再 send 一轮，让 CLI 自行修正，不打扰用户。

Proposal 格式（out/proposal.json，Runtime 契约核心对象）

{
  "kind": "create | modify | fix",
  "title": "追加 ControlNet Depth 分支",
  "summary": "基于参考图增加深度控制…原节点全部保留。",
  "ops": [                                       // 原子操作序列，按序应用
    { "op": "add_node",    "id": "n8",  "type": "LoadImage",
      "params": { "image": "ref_depth.png" } },
    { "op": "add_node",    "id": "n11", "type": "ControlNetApply",
      "params": { "strength": 0.85 } },
    { "op": "remove_edge", "from": ["n2","COND"], "to": ["n5","positive"] },
    { "op": "add_edge",    "from": ["n11","COND"], "to": ["n5","positive"] },
    { "op": "set_param",   "id": "n10", "key": "model",
      "prev": "depth-ctl-1.5",                   // 旧值由后端校验补全
      "value": "depth-ctl-2.0" },
    { "op": "set_param",   "id": "n2",  "key": "text",   // 编辑 prompt
      "prev": "产品摄影棚拍…",
      "value": "产品摄影棚拍，柔光，45° 俯拍，深色背景…" }
  ],
  "version_label": "+ ControlNet Depth"          // 应用后的版本名
}

操作类型共六种：add_node / remove_node / set_param / add_edge / remove_edge / move_node。前端的变更清单与 diff 视图由 ops 直接推导（add→+，set_param→~，remove→−）。

编辑即 set_param：节点的任何参数修改都是它——prompt（文生图 / 文生视频节点的 text 参数）、seed / steps / cfg、模型选择、分辨率等，不另设独立 op。「给节点加 prompt」就是对 text 参数的 set_param；新增带 prompt 的节点则直接在 add_node.params 里给出。两条配套规则：① 后端应用前自动校验并补全 prev 旧值，既驱动 diff 展示也做冲突检测（旧值对不上即基底已变，Proposal 转 superseded）；② 长文本参数（prompt）在 ProposalCard 的 diff 视图中渲染为前后对照（旧值划线、新值高亮），而非只显示参数名。

Proposal 校验（后端强制，不信任 Agent 输出）

  • 节点类型必须存在于 NodeRegistry；参数名与值必须落在 schema 与 catalog 参数域内。
  • 边的端口类型必须匹配（MODEL→MODEL 等）；应用后图必须是无环 DAG 且无悬空必填输入。
  • ops 在当前版本上可完整应用（基于版本号乐观锁——若用户已撤销/恢复导致基底变化，Proposal 标记 superseded 退回 Agent）。
  • 校验失败的 Proposal 以错误返回给 Agent 自行修正，不打扰用户。

06数据模型

SQLite 持久化（单文件 workbench.db，WAL 模式）。图快照与 Proposal 的 ops 体量大且不可变，存为工作区目录下的 JSON 文件，表中存路径 + 哈希。

表关键字段说明
workspacesid, name, created_at, cur_version_id顶栏的「产品图工作流」即一个工作区。
versionsid, workspace_id, idx, label, source(user|agent|fix|restore), graph_path, graph_hash, parent_id, created_at不可变快照。idx 即历史面板的 v0/v1/v2；undo 只移动 cur_version_id 指针，restore 追加新版本（source=restore）。
proposalsid, workspace_id, base_version_id, kind(create|modify|fix), title, summary, ops_path, state(pending|applied|dismissed|superseded|invalid), result_version_id?, message_id与触发它的聊天消息互链；applied 后记录产生的版本。
messagesid, workspace_id, role(user|agent|sys), text, kind(plain|status|proposal|error|runplan|sweep), ref_id?, attachment?, created_at聊天流。卡片类消息经 ref_id 指向 proposal / run。
runsid, workspace_id, version_id, label, trigger(user|agent), plan(json: runs, seed_list, overrides), status(queued|running|succeeded|failed|interrupted), error(json?), started_at, ended_at一次 Queue 或一次 Sweep 中的一跑；Sweep 用 group_id 关联。
run_stepsrun_id, node_id, state(pending|active|done|failed), dur_ms逐节点执行明细，驱动 RunDock 步骤条与画布高亮回放。
outputsid, run_id, node_id, file_path, seed, selected, meta(json)输出条数据；selected 支持 sweep 选优。
uploadsid, workspace_id, filename, file_path, sha256用户上传的参考图等；执行时由 Gateway 按 provider 要求以文件或 URL 传入。

图的规范模型（graph JSON）

{
  "nodes": {
    "n5": {
      "type": "KSampler",                  // NodeRegistry 中的节点类型
      "title": "KSampler",                 // 显示名（可被用户改）
      "params": { "seed": 843629104821, "steps": 28, "cfg": 6.5 },
      "pos": [520, 86]                     // GraphService 自动布局产出
    }, …
  },
  "edges": [
    { "from": ["n1","MODEL"], "to": ["n5","model"], "type": "MODEL" }, …
  ]
}
  • 编译：GraphService.compile() 把规范模型降为可执行计划：拓扑序 + 每节点的 provider 调用描述（能力、参数、输入依赖），交给 RunService 执行；「导出 workflow JSON」导出的是规范模型，便于分享与复用。
  • 端口类型着色：边的 type（MODEL/CLIP/VAE/LATENT/CONDITIONING/IMAGE/MASK）直接映射前端 --t-* 色 token，类型语义沿用 ComfyUI 习惯（用户熟悉）。
  • 布局：采用分层（longest-path layering）+ 简单重心排序；Proposal 预览时新节点布在受影响区域附近，避免全图重排跳动。

07API 契约（REST / WebSocket）

REST 承载「显式动作 + 初始加载」，WS 承载「一切异步事件」。所有路径前缀 /api；WS 单连接 /ws?workspace=<id>，事件为 { "ev": "...", "data": {…} }。

REST

路径说明
GET/api/workspaces/{id}/state全量状态对账：当前版本图、版本列表、消息流、pending proposal、运行历史、输出。前端启动与重连唯一入口。
POST/api/workspaces/{id}/messages发送用户消息 {text, attachments?}；立即返回 message id，Agent 响应走 WS。
POST/api/proposals/{id}/apply应用提议 → 校验、生成新版本、广播 version.committed。基底版本不符返回 409。
POST/api/proposals/{id}/dismiss忽略提议（同时通知 Agent 会话该提议被拒）。
POST/api/workspaces/{id}/undo版本指针后退一步。
POST/api/versions/{id}/restore以历史版本为内容追加新版本（source=restore）。
POST/api/workspaces/{id}/runs手动「运行 Queue」：编译当前版本并提交。画布为空或有 pending proposal 时 409（与原型禁用逻辑一致）。
POST/api/runs/confirm对 Agent 的运行请求（out/run_plan.json）作确认 {plan_id, approve: bool}。approve 后 RunService 开始执行。
POST/api/runs/{id}/interrupt中断：取消进行中的 API 调用与后续节点（sweep 剩余轮次取消）。
POST/api/workspaces/{id}/uploadsmultipart 上传参考图；落盘供节点参数引用。
GET/api/versions/{id}/export下载该版本 workflow JSON（规范模型，便于分享/复用）。
GET/api/connGateway / 各 provider 可用性、节点库版本与节点数、Agent runtime 状态（顶栏指示器）。
POST/api/outputs/{id}/select标记选中输出。

WebSocket 事件（服务端 → 前端）

事件载荷与触发时机
agent.status{message_id, text} — Agent 过程状态（"正在规划图变更…"），同一 message_id 原地更新；结束时 agent.status.end 移除。
agent.message{message} — Agent 正式回复（含 kind 与 ref_id，前端据此渲染 Proposal/错误/运行计划卡片）。
proposal.created / proposal.resolved提议入栈（画布开始预览）/ 终态（applied | dismissed | superseded）。
version.committed{version, cur_idx} — 任何新版本（应用/撤销/恢复）；前端刷新画布与历史面板。
run.requested{plan} — Agent 请求运行，前端弹确认框（版本/次数/预计成本/待确认变更/可中断）。
run.started / run.progress / run.done运行生命周期；progress ∈ [0,1] 按节点预估时长加权；done 含 status 与输出列表。
node.state{run_id, node_id, state, dur_ms?} — 驱动步骤条与画布节点高亮（active 脉冲 / done 勾 / failed 红标）。
run.failed{node_id, error:{raw, human}} — 失败即刻推送；随后 Agent 诊断消息经 agent.* 到达。
outputs.updated{outputs[]} — 输出条增量（sweep 每轮追加一张）。
conn.status{gateway: ok|degraded, providers: {seedance2: ok, …}, node_defs: 312, agent: ok|down} — 后端 10s 心跳探测。

客户端 → 服务端方向不经 WS（统一走 REST），避免双通道写入的竞态与重试歧义。

08关键状态机与时序

Proposal 生命周期

drafting→ pending→ applied
pending 还可 → dismissed（用户忽略） superseded（基底版本变化） invalid（校验失败，退回 Agent）

同一工作区同时至多一个 pending Proposal；存在 pending 时「运行 Queue」禁用（提示「请先处理待确认的图变更」），Agent 确认弹窗会标注「待确认变更：有 — 将先被忽略」。

Run 生命周期

queued→ running→ succeeded
running 还可 → failed（节点报错） interrupted（用户中断）

时序 A · 失败 → 诊断 → 最小修复闭环（原型「修复报错」流）

#参与方动作
1RunService → GatewayDAG 执行器按拓扑序执行，至 #10 节点 Gateway 调用 provider 返回 model_not_found（请求的 depth-ctl-1.5 已下线）。
2RunService → 前端node.state(failed) + run.failed{raw, human}：画布红标失败节点并自动选中，RunDock 转失败态，聊天插入错误卡片。
3RunService → Orchestrator把错误上下文（节点、参数、traceback）写入 ctx/run_error.json，经 Runtime 层 send 诊断请求。
4Agent CLI按 fix_error skill 读 ctx/run_error.json + ctx/catalog.json，发现 depth-ctl-2.0 可用 → 写出 out/proposal.json（kind=fix，仅 1 个 set_param op）。
5用户查看修复提议（"只改一个参数，不动其它节点"）→ 应用 → 新版本（source=fix）→ 重新运行成功。

时序 B · Agent 发起 Seed Sweep（成本守门）

#参与方动作
1Agent CLI写出 out/run_plan.json（runs: 4，seed_list: […]）— 仅生成计划，不执行。
2后端 → 前端run.requested，弹确认框：版本、4 次（预计 4 次 Seedance 2 调用 · 估算成本）、待确认变更、可中断。
3用户确认POST /api/runs/confirm{approve:true}；若取消，计划作废并告知 Agent。
4RunService串行 4 轮（每轮覆盖 seed 重编译执行），outputs.updated 每轮追加；任一时刻可中断，剩余轮次取消。
5Agent读取 4 轮结果 → 回复选优建议（sweep 卡片），后端把推荐输出置为 selected。

版本栈语义

  • 提交：应用 Proposal 时在 cur_idx 之后截断并追加（同原型 commitVersion），保证线性历史。
  • 撤销：仅指针后移，不删数据；前进留待 redo（v1.1）。
  • 恢复：复制历史快照追加为新版本，绝不改写历史——历史面板中任何 v 永远可信。

09安全与确认机制

双层守门

层守什么机制
图守门工作流被错误/意外修改Propose-then-Apply：画布预览 + 变更清单 + diff；应用前图纹丝不动；应用后可一键撤销。
成本守门API 配额被未经同意消耗Agent 触发的一切模型 API 调用必须经确认弹窗；确认内容含次数与预计成本；运行全程可中断；config 可设每日成本上限。用户手动 Queue 视为已同意。

进程与边界控制

  • 网络面：后端只绑定 loopback；唯一出网面是 Gateway 到各模型 API、CLI 到其自身推理 API。模型 API 密钥由 Gateway 统一持有，存 config.toml 引用的环境变量，绝不入库、不进日志、也绝不进入 Agent 会话目录。
  • Agent 沙箱：CLI 以各自原生沙箱模式启动（codex：workspace-write；Claude Code：目录白名单），可读写区域仅限会话工作目录，shell 执行禁用；ctx/ 中只注入图、节点定义与错误信息，不注入用户文件系统内容。
  • 路径安全：uploads 与 graphs 的读写严格限制在工作区目录内（路径规范化 + 前缀校验）；ctx/catalog.json 仅含模型名与参数域，绝不含密钥。
  • 输入校验：所有 Agent 产出（proposal ops、run plan）经 JSON Schema 校验 + 语义校验（§05），等同对待不可信输入。

10部署与目录结构

交付为单一静态二进制：cargo 构建，前端产物经 rust-embed 嵌入，下载即用（或 brew install comfyui-agent）。运行 comfyui-agent 启动服务并自动打开浏览器——单进程、单端口、零运行时依赖（Codex CLI / Claude Code 需单独安装，启动时探测可用 runtime）。Provider 密钥与 runtime 路径在 config.toml 配置，首次启动有引导页校验密钥连通性。
